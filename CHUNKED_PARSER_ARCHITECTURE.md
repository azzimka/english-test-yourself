# Архитектурное решение: Масштабируемый Чанкинг-Парсер тестов (Groq API)

## 📌 1. Контекст проблемы и цель задачи

### Проблема:
* Учителя загружают тесты разного объёма — от коротких срезов (10–15 вопросов) до олимпиад и итоговых диагностических тестов на **40, 70, 100 и более заданий**.
* При попытке скормить большой тест (40+ заданий) в **один** запрос к нейросети возникает фатальное ограничение по длине генерации (**Output Token Limit**):
  * Для 40 вопросов JSON занимает ~4000 токенов (из-за вариантов ответов, текстов чтения и ключей).
  * Для 100 вопросов JSON потребует **10 000 – 12 000 токенов вывода**.
  * Если `max_tokens` не настроен или лимит превышен: модель либо «лениво» обрезает тест (например, закрывает JSON на 28 вопросах), либо обрывает вывод посередине с ошибкой `JSONDecodeError`.
* **Почему НЕ Gemini:** В Google AI Studio аккаунт упёрся в жесткий лимит 20 запросов в день (RPD 19/20) и предупреждение о балансе (`Prepay credits depleted`). Покупка платного тарифа не рассматривается.
* **Почему Groq:** Groq API абсолютно **бесплатен**, имеет высокую квоту (30 запросов в минуту), флагманскую модель **`openai/gpt-oss-120b`** (или `openai/gpt-oss-20b`, `qwen/qwen3.8-27b`), поддерживает до **8192 токенов вывода на запрос** и работает со скоростью 500+ токенов в секунду.

### Цель задачи:
Реализовать в `services/ai_parser.py` надёжный **асинхронный параллельный чанкинг (пакетную обработку)** на базе **Groq API**:
1. Любой тест (хоть на 40, хоть на 100, хоть на 200 вопросов) должен парситься **без потери единого вопроса**.
2. Обработка должна занимать не более 5–8 секунд благодаря параллельным вызовам через `asyncio.gather`.
3. Сохранять контекст для текстов чтения (*Reading passages*) и автоматически учитывать общий блок ключей (*Answer Key*), даже если он находится в самом конце документа.

## 🧩 3. Детальные требования к реализации

### Шаг 1: Извлечение Answer Key (Блока ответов)
В тестах по английскому языку на последней странице часто идёт блок вида:
```text
ANSWER KEY & SCORE GUIDE
1 A 2 B 3 B 4 A 5 B ... 40 B
```
Если мы разделим текст на 3 блока (вопросы 1–30, 31–60, 61–100), то блоки 1 и 2 **не увидят ключи**, потому что ключи находятся внизу документа.
* **Требование:**  
  Написать регулярное выражение / эвристику, находящую секцию ответов:
  `re.search(r"(?:ANSWER\s*KEY|ANSWERS|KEYS|ОТВЕТЫ|КЛЮЧИ)[\s\S]*$", text, re.IGNORECASE)`
* Если такой блок найден, мы извлекаем его в отдельную строку `answer_keys_text`.
* Эту строку мы передаём **в каждый чанк** как контекст для нейросети! Тогда каждый чанк знает правильные ответы для своих заданий.

### Шаг 2: Умное разбиение на чанки (Chunking)
Нельзя делить текст тупо по количеству символов, иначе:
* Вопрос разорвётся посередине предложения.
* Текст для чтения (*Reading Text*) оторвётся от связанных с ним вопросов.

**Алгоритм разделения:**
1. Находим границы вопросов по паттерну начала задания:  
   `re.compile(r"(?:\n|^)\s*(?:\d+[\.\)]|[Q|q]uestion\s+\d+)")`
2. Если обнаружен маркер секции чтения (например `Text 1:`, `Text 2:`, `Passage 1`, `Read the text`):
   Весь связанный текст и все вопросы к нему должны попасть **в один чанк**.
3. Целевой размер одного чанка: **20–25 вопросов**.
   * Тест на 40 вопросов -> 2 чанка (например, 1–25 и 26–40).
   * Тест на 100 вопросов -> 4 чанка по 25 вопросов.

### Шаг 3: Промпт для чанка
Для каждого пакета заданий формируется компактный системный промпт:
```python
CHUNK_PROMPT = """You are an expert English exam parser.
Your task is to parse a SPECIFIC BATCH of questions from an English test into JSON format.

CRITICAL RULES:
1. Parse EVERY SINGLE question present in this batch without omitting or summarizing any.
2. If multiple-choice options (A, B, C, D) exist, put them into `options`.
3. If an Answer Key is provided below, use it to accurately fill `correct_answer`.
4. Keep `explanation` very brief (1 short sentence) or null to save tokens.
5. If questions refer to a reading passage in this batch, include that text in `context_text`.

Output MUST be a valid JSON object:
{
  "questions": [
    {
      "question_text": "string",
      "context_text": "string or null",
      "options": ["string"],
      "correct_answer": "string",
      "explanation": "string or null"
    }
  ]
}
"""
```

### Шаг 4: Параллельная обработка через `asyncio.gather`
Вместо последовательного ожидания запускаем все пакеты одновременно:
```python
tasks = [
    parse_single_chunk(client, chunk, answer_keys_text, model_name)
    for chunk in chunks
]
chunk_results = await asyncio.gather(*tasks)
```
* Лимит Groq — **30 запросов в минуту (RPM)**. 3–5 параллельных запросов для одного 100-вопросного теста абсолютно укладываются в лимит.
* Если один из чанков временно упал по Rate Limit (429), используем декоратор `tenacity` с exponential backoff (1-2 сек).

### Шаг 5: Склейка и заголовок
1. **Заголовок теста (`title`):**  
   Извлекается отдельным быстрым микро-запросом по первому экрану текста (первые 500 символов), либо берётся из первого чанка.
2. **Склейка вопросов:**  
   `all_questions = []`  
   Для каждого блока добавляем `chunk_questions`.
3. **Проверка целостности:**  
   Проверяем, что общее число вопросов совпадает с количеством заданий в исходнике.
4. Формируем итоговый `ParsedTest(title=title, description=desc, questions=all_questions)`.

## ⚙️ 5. Конфигурация вызовов Groq (Рецепт успеха)

При вызове `client.chat.completions.create` обязательно передавать:
```python
completion = await client.chat.completions.create(
    model="openai/gpt-oss-120b", # или GROQ_MODEL
    messages=[
        {"role": "system", "content": CHUNK_PROMPT},
        {"role": "user", "content": chunk_user_content}
    ],
    response_format={"type": "json_object"},
    temperature=0.1,             # Минимальная температура для точности
    max_tokens=8192              # ОБЯЗАТЕЛЬНО! Не даёт Groq обрезать длинные ответы
)
```
Фоллбэк-модели при сбое квоты:
1. `openai/gpt-oss-120b` (основная)
2. `openai/gpt-oss-20b` (быстрый резерв)
3. `qwen/qwen3.8-27b` (резерв с большим контекстом)
